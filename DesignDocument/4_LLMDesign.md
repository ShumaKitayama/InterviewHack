# 4. AI / LLM 設計

## 4.1 目的と位置づけ

- 本プロダクトのコア価値は「AIによる面接改善ループの自動化」にある
- LLMは以下の用途で使用する
  - 事前対策：想定質問 + 模範解答の生成
  - 事後対策：実際の回答の添削 + 改善案生成
  - 要約：次回直すべきポイントの要約生成
- ユーザーはプロンプトを意識せず、構造化データ（自己資産・企業情報・面接ログ）を入力すればよい設計とする

---

## 4.2 AIユースケース定義

### 4.2.1 想定Q&A生成（事前対策）

- 入力
  - 自己資産データ（Asset）
  - 企業情報データ（Company）
  - 募集職種
- 出力
  - 想定質問リスト（例：10問）
  - 各質問に対する模範解答
  - 各回答で参照した自己資産のID/要約
- 品質要件
  - 質問は「深掘りされやすい」観点になっていること
  - 回答は自己資産に基づき、具体例・数値・学びを含むこと
  - 一般論テンプレにならないこと

### 4.2.2 面接ログ添削（事後対策）

- 入力
  - 実際の質問テキスト
  - ユーザーの回答テキスト
  - 自己資産データ
- 出力
  - 問題点の指摘（論理性・具体性・説得力・構成などの観点）
  - 改善案の要点リスト
  - 改善版の回答案
  - 参照した自己資産
- 品質要件
  - 否定だけでなく「どう直せば良いか」が具体的に示されること
  - 自己資産のどのエピソードを使ったかが分かること

### 4.2.3 要約生成（ダッシュボード用）

- 入力
  - 直近の面接ログ添削結果（複数件）
- 出力
  - 次回の面接で特に意識すべきポイントの短文要約（3〜5項目程度）
- 品質要件
  - 抽象論ではなく行動に落とせる表現になっていること

### 4.2.4 企業研究資料の要約・構造化（ES準備）

- 入力
  - スクレイピングしたWebページテキスト
  - アップロードされたPDFの抽出テキスト
  - ユーザーのメモ
- 出力
  - 企業の魅力・特徴（3点要約）
  - 求める人物像
  - 最近のニュース・トピック
- 品質要件
  - ノイズ（広告、ヘッダー/フッター）を除去する
  - 「なぜこの会社か」に使えそうな情報を優先抽出する

### 4.2.5 ESドラフト生成（セット1＋セット2統合）

- 入力
  - ターゲット企業・職種情報（Company）
  - 企業研究資料の要約（ResearchMaterial / セット2）
  - 選択された自己資産（Assets / セット1）
  - ESセクションのテーマ（例：「志望動機」「自己PR」）
  - 文字数制限
- 出力
  - 指定テーマに沿ったES原稿ドラフト
  - 論理構成の解説（なぜこのエピソードを選んだか）
- 品質要件
  - 企業の特徴（セット2）と自分の強み（セット1）の接点を明確にする
  - 指定文字数の±10%以内に収める
  - 結論ファースト（PREP法）を意識する

### 4.2.6 ES推敲・ブラッシュアップ

- 入力
  - 現在のES原稿
  - ユーザーからの修正指示（例：「もっと具体的に」「熱意を強調して」）
  - （任意）企業の求める人物像
- 出力
  - 修正版ES原稿
  - 変更点の解説
- 品質要件
  - 指示を的確に反映しつつ、文章の自然さを保つ

## 4.3 プロンプト設計方針

### 4.3.1 ロール分離

- System: 「あなたは凄腕の面接官・キャリアコーチです」
- Developer: 出力フォーマット、評価観点、禁止事項、文字数制約などを定義
- User: 構造化された入力データ（自己資産、企業情報、質問、回答など）

### 4.3.2 入力スキーマ（例）

- 自己資産:
  - id, type, title, content, tags
- 企業情報:
  - name, job_title, selection_phase, motivation_memo
- 面接ログ:
  - question_text, answer_text

※ 実際の送信時はトークン削減のため、要約済み形式も併用する

### 4.3.3 出力フォーマット

- 原則 JSON 形式で返す
  - questions: [ { question, answer, referenced_assets[] } ]
  - feedback: { issues[], improvements[], improved_answer, referenced_assets[] }
- フロントエンドはこのJSONをレンダリングするだけでUIが組める設計にする
- 自由文のみの出力は禁止

### 4.3.4 トーン・制約

- トーン: 厳しめだが建設的、面接官 + コーチ視点
- 制約例:
  - 回答は最大 N 文字
  - STAR法などのフレームワークを意識する
  - 事実にない経歴を捏造しない
  - 「一般論」だけで終わらせない

---

## 4.4 モデル選定方針

- デフォルトモデル:
  - コスト重視: 軽量・低コストモデル（例: gpt-4o-mini クラス）
- 高品質モード（Pro向け）:
  - 添削・改善案生成のみ上位モデルを使用
- 切り替え基準:
  - トークン量
  - 重要度（添削 > 事前Q&A生成）
  - ユーザーのプラン種別

---

## 4.5 コスト最適化戦略

- 入力圧縮
  - 自己資産は全文ではなく「要約 + 重要タグ」に変換して送信
- キャッシュ
  - 同一条件（同じ企業 + 同じ自己資産セット）の生成結果は再利用
- 差分生成
  - 「質問だけ再生成」「回答だけ再生成」を可能にし、再計算コストを削減
- 利用制限
  - Freeプランは月間回数制限
  - GenerationJobでトークン・コストを記録し、上限超過を防止

---

## 4.6 品質担保・評価ルーブリック

- 想定Q&A生成の評価観点
  - 質問が具体的か
  - 回答が自己資産に基づいているか
  - 数値・成果・学びが含まれているか
- 添削の評価観点
  - 指摘が具体的か
  - 改善案がそのまま使えるレベルか
  - 元の回答との差分が明確か
- 定期的にサンプル入力で回帰テストを行う

---

## 4.7 ハルシネーション・安全対策

- 企業情報はユーザー入力または明示的に許可した情報のみ使用
- 自己資産に存在しない経歴・実績を「作らない」よう明示的に指示
- 出力に「仮定」「推測」を含む場合は必ず注記させる
- 差別的表現・違法行為・経歴詐称を助長する表現は禁止

---

## 4.8 失敗時の挙動設計

- APIエラー / タイムアウト
  - リトライボタン表示
  - 入力内容は保持（再入力させない）
- 出力フォーマット不正
  - バックエンド側で再パース・再リクエスト
- 利用制限超過
  - 制限理由・次回リセット日・アップグレード導線を表示

---

## 4.9 ログ・監視・運用

- GenerationJob に以下を記録
  - ジョブ種別、モデル、トークン使用量、推定コスト、成功/失敗
- ダッシュボード用の集計
  - ユーザーあたり月間生成回数
  - 機能別のコスト比率（事前生成 / 添削 / 要約）
- 異常検知
  - 失敗率急増
  - コスト急増
