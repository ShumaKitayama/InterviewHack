# 4. AI連携（プロンプト生成・取り込み）設計

> 改訂：2026-10-22。方針転換メモ（`DirectionChange_20261022.md`）の決定事項 D1〜D16 と、2.10 の共通契約を反映した。
> 旧版の「LLM API をサーバーから呼ぶ」設計は廃止し、コピペ方式（D7）に置き換えた。

## 4.1 目的と位置づけ

- 本プロダクトのコア価値は「AIによる面接改善ループ」を、**運営費0円・APIキーなし**で回せることにある
- アプリは LLM の API を呼ばない（D7）。AI を使う機能はすべて「AI連携」（1.1.0）で実現する
  1. **プロンプト生成**：Go BFF が、構造化データ（自己資産・企業情報・面接ログ・企業研究資料）とテンプレートからプロンプトを組み立てる
  2. **外部AIでの実行**：ユーザーが共有シートまたはクリップボードで ChatGPT・Gemini などに渡す（ユーザー自身のアカウント、無料版でもよい）
  3. **回答の取り込み**：ユーザーが回答を貼り戻す。Go BFF が解析してプレビューを返し、ユーザーが確認・修正してから保存する（D10）
- アプリの責務は「材料の整理」「質の高いプロンプトの組み立て」「回答の構造化と蓄積」である
- ユーザーはプロンプトを自分で組む必要はない。ただし、外部に渡す前にプロンプトの内容を確認できる（4.7）
- テンプレート生成と解析は、Go の Domain 層（`internal/domain/service/prompt`）に純粋関数として置く（2.10.4）

---

## 4.2 ユースケース定義

ユースケースとテンプレートの初期バージョンは、共通契約 2.10.1 に従う。

| use_case | 内容 | 初期 template_version | 回答の解析 |
|----------|------|----------------------|-----------|
| `qa_generate` | 想定Q&A生成 | `qa-v1` | する |
| `answer_review` | 面接ログ添削 | `review-v1` | する |
| `summary_generate` | ダッシュボード要約 | `summary-v1` | しない（全文） |
| `research_summarize` | 企業研究資料の要約 | `research-v1` | する |
| `es_generate` | ESドラフト | `esdraft-v1` | しない（全文） |
| `es_refine` | ES推敲 | `esrefine-v1` | しない（全文） |

各テンプレートの骨子では、`{...}` が差し込み、`【...】` が出力形式の目印を表す。

### 4.2.1 想定Q&A生成（事前対策：`qa_generate` / `qa-v1`）

- 入力（プロンプトに含めるデータ）
  - 企業情報：企業名、職種、選考フェーズ、志望動機メモ（`companies`）
  - 企業研究資料：ユーザーが選んだ資料。`summary` があれば `summary` を、なければ `content_raw` を使う（4.3.5）
  - 自己資産：ユーザーが選んだもの（種別、タイトル、本文、タグ）
  - オプション：質問数（初期値 10）
- テンプレート骨子

```
あなたは{職種}の採用面接を担当する経験豊富な面接官であり、キャリアコーチです。
以下の候補者情報と企業情報をもとに、この面接で聞かれやすく、深掘りされやすい質問を{質問数}問作り、
それぞれに候補者本人の経験だけを使った模範解答を書いてください。

# 制約
- 候補者情報に書かれていない経歴・実績・数値を作らないこと
- 推測を含む場合は、その文の末尾に（推測）と書くこと
- 模範解答は1問あたり{文字数目安}字程度。結論→理由→具体例→学びの順で書くこと
- 一般論だけで終わらせないこと

# 企業情報
{企業名} / {職種} / {選考フェーズ}
{志望動機メモ}
{企業研究資料（選択分）}

# 候補者情報（自己資産）
{自己資産の一覧：[種別] タイトル：本文}

# 出力形式（この形式以外の文章は書かないこと）
1行目に必ず「【形式:qa-v1】」と書き、続けて以下を質問数だけ繰り返してください。
【Q1】質問文
【A1】模範解答
【意図1】この質問で面接官が確認したいこと
```

- 解析結果（プレビュー）：`{ items: [{ questionText, answerText, intentText }] }`
- 保存先：`qa`（`source_type = pre_generated`）。プロンプトに使った自己資産は `qa_asset_relations` に紐付ける
  - `【意図N】`（`intentText`）はプレビューに表示するだけで、保存しない（`qa` に意図のカラムは持たない。7.5.5 の commit も `questionText` と `answerText` だけを受け取る）
- 品質要件
  - 質問は「深掘りされやすい」観点になっていること
  - 回答は自己資産に基づき、具体例・数値・学びを含むこと
  - 一般論のテンプレートにならないこと

### 4.2.2 面接ログ添削（事後対策：`answer_review` / `review-v1`）

- 入力
  - 面接ログ：実際の質問、ユーザーの回答、自己評価（`interview_logs`）
  - 面接情報：企業名、職種、フェーズ（`interviews` / `companies`）
  - 自己資産：ユーザーが選んだもの
  - オプション：厳しさ（`normal` / `hard`）
- テンプレート骨子

```
あなたは{職種}の採用面接官であり、厳しめだが建設的なキャリアコーチです。
以下は候補者が実際の面接で受けた質問と、その場での回答です。
論理性・具体性・説得力・構成の観点で添削し、次回使える改善後の回答を書いてください。

# 制約
- 否定だけで終わらせず、「どう直せばよいか」を具体的に書くこと
- 改善後の回答には、候補者情報にあるエピソードだけを使うこと。新しい経歴を作らないこと
- 使ったエピソードのタイトルを改善案の中で明記すること

# 質問
{質問文}
# 候補者の回答
{回答文}
# 自己評価
{自己評価}
# 候補者情報（自己資産）
{自己資産の一覧}

# 出力形式（この形式以外の文章は書かないこと）
【形式:review-v1】
【指摘】
- 指摘（観点：論理性 / 具体性 / 説得力 / 構成 のいずれかを先頭に書く）
【改善案】
- 改善の要点
【改善後の回答】
改善後の回答文
```

- 解析結果（プレビュー）：`{ issues: string[], improvements: string[], improvedAnswerText: string }`
- 保存先：`interview_logs.ai_feedback_text`（指摘と改善案）、`interview_logs.ai_improved_answer_text`（改善後の回答）。ユーザーが選んだ場合は、`qa`（`source_type = review_improved`）にも登録する
- 品質要件
  - 否定だけでなく、「どう直せばよいか」が具体的に示されること
  - 自己資産のどのエピソードを使ったかが分かること

### 4.2.3 ダッシュボード要約（`summary_generate` / `summary-v1`）

- 入力
  - 直近の面接ログ添削結果（`interview_logs.ai_feedback_text`、複数件）。対象は面接単位または直近 N 件
- テンプレート骨子

```
以下は、ある就活生の直近の面接に対する添削結果です。
次の面接で特に意識すべきポイントを3〜5項目、行動に移せる短文で箇条書きにしてください。

# 添削結果
{添削結果の一覧}

# 出力形式
1行目に「【形式:summary-v1】」と書き、続けて箇条書きだけを書いてください。
```

- 取り込み：解析しない。形式行を取り除き、全文を `dashboard_summaries.content` に保存する（`source_interview_id` は面接単位の場合のみ設定）
- 品質要件：抽象論ではなく、行動に落とせる表現になっていること

### 4.2.4 企業研究資料の要約（ES準備：`research_summarize` / `research-v1`）

- 入力
  - 対象の企業研究資料 1 件の `content_raw`（端末で抽出したテキスト。D11）
  - 企業名、職種、ユーザーのメモ
- テンプレート骨子

```
以下は{企業名}に関する資料の本文です（Webページや PDF から抽出したもので、ノイズを含むことがあります）。
{職種}志望の就活生が「なぜこの会社か」を語るために使える情報を整理してください。

# 制約
- 広告、メニュー、ヘッダー、フッターなどのノイズは無視すること
- 資料に書かれていないことは書かないこと

# 資料本文
{content_raw}

# 出力形式（この形式以外の文章は書かないこと）
【形式:research-v1】
【魅力・特徴】
- 3点
【求める人物像】
本文
【最近のトピック】
- 箇条書き
```

- 解析結果（プレビュー）：`{ highlights: string[], idealCandidate: string, recentTopics: string[] }`（7.5.5）
- 保存先：`research_materials.summary`。保存時は、3 つの見出しを付けたテキストに整形して保存する
- 品質要件
  - ノイズ（広告、ヘッダー、フッター）を除去する
  - 「なぜこの会社か」に使えそうな情報を優先して抽出する

### 4.2.5 ESドラフト（`es_generate` / `esdraft-v1`）

- 入力
  - 企業情報（企業名、職種）
  - 企業研究資料：ユーザーが選んだもの（`summary` 優先）
  - 自己資産：ユーザーが選んだもの
  - ESセクション：テーマ（`es_sections.title`）、文字数制限（`character_limit`）
- テンプレート骨子

```
あなたは新卒・転職のES添削を専門とするキャリアコーチです。
以下の企業情報と候補者情報を使い、「{セクション名}」のES原稿を書いてください。

# 制約
- 企業の特徴と、候補者の強み・経験の接点を明確にすること
- 結論ファースト（PREP法）で書くこと
- {文字数制限}字の±10%以内に収めること
- 候補者情報にない経歴・実績・数値を作らないこと

# 企業情報
{企業名} / {職種}
{企業研究資料（選択分）}
# 候補者情報（自己資産）
{自己資産の一覧}

# 出力形式
1行目に「【形式:esdraft-v1】」と書き、続けてES本文だけを書いてください。解説や前置きは書かないこと。
```

- 取り込み：解析しない。形式行を取り除き、全文を `es_sections.content_draft` に取り込む（プレビュー上で編集可）
- 使った自己資産と資料は `es_project_asset_relations` / `es_project_research_material_relations` に紐付ける
- 品質要件
  - 企業の特徴（セット2）と自分の強み（セット1）の接点を明確にする
  - 指定文字数の±10%以内に収める（プレビューで文字数と、範囲外であることの警告を表示する）
  - 結論ファースト（PREP法）を意識する

### 4.2.6 ES推敲（`es_refine` / `esrefine-v1`）

- 入力
  - 現在のES原稿（`es_sections.content_draft`）
  - ユーザーの修正指示（例：「もっと具体的に」「結論ファーストで」「熱意を強調して」）
  - 文字数制限
  - （任意）企業研究資料の「求める人物像」
- テンプレート骨子

```
以下のES原稿を、修正指示に従って書き直してください。

# 修正指示
{修正指示}
# 制約
- {文字数制限}字の±10%以内に収めること
- 原稿にない経歴・実績・数値を加えないこと
- 文章の自然さを保つこと
# 現在の原稿
{原稿}
# （任意）企業の求める人物像
{求める人物像}

# 出力形式
1行目に「【形式:esrefine-v1】」と書き、続けて書き直したES本文だけを書いてください。
```

- 取り込み：解析しない。形式行を取り除いた全文を新しい `content_draft` として取り込む。取り込む前に、元の原稿との差分をプレビューで表示する
- 品質要件：指示を的確に反映しつつ、文章の自然さを保つ

## 4.3 プロンプト設計方針

### 4.3.1 ロール指示はプロンプト本文に含める

- 外部AIサービスの画面に貼り付けるため、System / Developer / User の区別は使えない
- 1つのプロンプトを、次の順序で構成する
  1. ロール（例：「あなたは{職種}の採用面接官であり、キャリアコーチです」）
  2. 依頼内容
  3. 制約（禁止事項、文字数、フレームワーク）
  4. 入力データ（見出し付き）
  5. 出力形式（形式行と目印）
- 出力形式の指示は必ず最後に置く（入力データが長くても、指示が埋もれないようにする）

### 4.3.2 入力データの書式

- 自己資産：`[種別] タイトル（タグ）：本文`
- 企業情報：企業名 / 職種 / 選考フェーズ / 志望動機メモ
- 面接ログ：質問文 / 回答文 / 自己評価
- 企業研究資料：`[資料タイトル]` に続けて、`summary` または `content_raw`
- 入力データ内の `【` `】` は、全角の別記号に置き換える（目印との衝突を防ぐ）

### 4.3.3 出力形式（目印付きテキスト）

- JSON は使わない。人が読める目印付きテキストにする（D10）
  - 無料版の LLM でも崩れにくく、外部AIの画面上でもそのまま読め、手で直しやすいため
- 回答の 1 行目に、形式行 `【形式:<template_version>】` を出すよう指示する
- 目印は 2.10.1 の共通契約に従う

### 4.3.4 トーン・制約

- トーン：厳しめだが建設的。面接官とコーチの両方の視点
- 共通の制約
  - 事実にない経歴・実績・数値を作らない
  - 推測を含む場合は（推測）と注記する
  - 結論→理由→具体例→学び（STAR / PREP）を意識する
  - 一般論だけで終わらせない
  - 文字数の目安を明示する

### 4.3.5 プロンプトの長さと資料の選択

- プロンプトに入れる自己資産と企業研究資料は、ユーザーが選ぶ（1.1.0）。選んだ ID とオプションは `prompt_sessions.input_refs` に保存する（本文は保存しない。D13）
- 企業研究資料は、`summary` があれば `summary` を使う。なければ `content_raw` を使う
- プロンプト全体の推奨上限は 8,000 文字とする
  - 上限を超える場合は、プロンプト生成時に警告を返す。アプリは「資料を減らす」か「先に資料を要約する（4.2.4）」よう案内する
  - `content_raw` を使う資料は、1 件あたり先頭 3,000 文字までに切り詰め、切り詰めたことをプロンプト内に注記する
- `research_summarize` は資料 1 件を対象とし、`content_raw` 全体（上限 8,000 文字まで）を使う

### 4.3.6 テンプレートのバージョニング

- テンプレートは `use_case` × `template_version` で識別する（例：`qa-v1`）
- 出力形式（目印）を変える変更は、新しいバージョンとして追加する。文言だけの改善も、回帰テスト（11章）で差が出る場合は新しいバージョンにする
- 新しいプロンプトは、各 use_case の最新バージョンで生成する
- 解析器は、過去のバージョンもすべて解析できる状態を保つ（古い回答を貼り戻しても解析できるようにする）
- `prompt_sessions.template_version` に、生成時のバージョンを記録する

### 4.3.7 解析ルール

- 解析は Go BFF の `POST /prompt-sessions/{id}/parse` で行う。この API はセッションの状態（`status = pasted`、`parse_result`、`pasted_at`）以外は何も保存しない（2.10.3）
- 解析しないユースケースも、保存の前に必ず parse を経由する（`created` から直接 `commit` はできない。7.6.1）
- 入力の上限は 100,000 文字とする（7.5.5）
- バージョンの判定
  - 回答の中の形式行 `【形式:...】` を優先する
  - 形式行がなければ、セッションの `template_version` を使う
  - 形式行の前後にある前置きや後書き（「はい、以下です」など）は無視する
- 解析の結果（`parse_result`）
  - `success`：必須の目印がすべて見つかった
  - `partial`：一部だけ見つかった（例：Q はあるが A がない項目がある）。見つかった分をプレビューに出し、欠けた箇所を `warnings` で返す
  - `failed`：目印が1つも見つからない。全文を 1 つの編集欄としてプレビューに出し、手動での分割・修正を促す
- 表記揺れの吸収：半角の `[ ]`、全角と半角の数字、目印の前後の空白、Markdown の装飾（`**`、`#`、箇条書き記号）を許容する
- 解析しないユースケース：形式行があれば取り除き、全文を 1 つの本文として返す（`parse_result = success`）
- 警告（`warnings`）の例：項目数が指定数と違う、文字数制限の範囲外、（推測）の注記がある
- 保存は `POST /prompt-sessions/{id}/commit` で、ユーザーが確認・修正した内容を受け取って行う

## 4.4 外部AIサービスの前提

- 対象：ChatGPT、Gemini など、ユーザーが使っている任意のチャット型AIサービス。無料版を前提にテンプレートを設計する
- アプリは特定のサービスに依存しない。iOS の共有シートで渡すため、受け渡し先はユーザーが選ぶ
- モデルの選定・切り替えは、運営側では行わない。品質はテンプレートで担保する
- 運営側のサーバーは、外部AIサービスにデータを送らない（1.2.4）

---

## 4.5 外部AIの揺れへの対処

コストの最適化は不要になった（LLM の API 費用が発生しない）。代わりに、運営側で制御できない外部AIの出力の揺れに対処する。

- 形式の崩れ：4.3.7 の解析ルール（表記揺れの吸収、部分成功、手動修正）で吸収する
- 前置きや後書き：形式行より前と、最後の目印ブロックより後の、目印のない文章は無視する
- 途中で止まる：無料版の出力上限で途中までしか出力されない場合は、`partial` として扱い、「続きを書いて」と依頼するようユーザーに案内する
- 文字数のずれ：プレビューで文字数を表示し、範囲外なら警告する
- 再生成：同じ `input_refs` からプロンプトを作り直せる（`GET /prompt-sessions/{id}/prompt`）。条件を変える場合は、新しいセッションを作る

## 4.6 品質担保・評価ルーブリック

- 想定Q&A生成の評価観点
  - 質問が具体的か
  - 回答が自己資産に基づいているか
  - 数値・成果・学びが含まれているか
- 添削の評価観点
  - 指摘が具体的か
  - 改善案がそのまま使えるレベルか
  - 元の回答との差分が明確か
- ESドラフト・推敲の評価観点
  - 企業の特徴と自分の強みの接点が明確か
  - 文字数制限の±10%以内か
- 回帰テスト（11章）
  - 固定入力セットに対して生成したプロンプトのスナップショットを比較する
  - 外部AIの回答サンプル（崩れた例を含む）に対して、解析結果を検証する

## 4.7 ハルシネーション・安全対策

- テンプレートに必ず含める指示
  - 候補者情報（自己資産）にない経歴・実績・数値を作らない
  - 推測を含む場合は（推測）と注記する
  - 企業情報は、ユーザーが入力した情報と、ユーザーが取り込んだ資料だけを使う
- 経歴詐称の防止：経歴の捏造や詐称を助長する出力を求めない。差別的表現・違法行為を求める指示は入れない
- 外部に渡す前の注意喚起（アプリ側）
  - 初回の AI連携時と、プロンプトの確認画面に、次の点を表示する
    - プロンプトには自己資産や企業情報など、入力したデータが含まれること
    - 外部AIサービスでの扱いは、各サービスの規約・設定（学習への利用など）に従うこと
    - 他人の個人情報や、機密情報（社外秘の資料など）を含めないこと
  - ユーザーは、外部に渡す前にプロンプトの全文を確認・編集できる
- 取り込み時：（推測）の注記がある箇所は、プレビューで警告として表示する

## 4.8 失敗時の挙動設計

- 解析の失敗（`failed` / `partial`）
  - 貼り戻した内容は失われない。プレビュー上で手動修正・分割してから保存できる（1.2.2）
  - 「形式行から外部AIに貼り直す」ための案内（例：「上の形式で出力し直して」とAIに依頼）を表示する
- 離脱（プロンプトを作ったが、回答を貼り戻さない）
  - `prompt_sessions.status` は `created`（解析後なら `pasted`）のまま残り、ダッシュボードの「未完了の AI連携」から再開できる（1.1.8）
  - ユーザーが明示的に中止した場合は `POST /prompt-sessions/{id}/abandon` で `abandoned` にする
  - 作成から 7 日を過ぎても `created` / `pasted` のままのものは `abandoned` にする（D13。定期ジョブは持たず、一覧の取得時に更新する。7.9）
- 通信の失敗：プロンプト生成・解析・保存はオンラインが必要（D16）。失敗時は再試行を案内し、貼り戻した内容は端末上に保持する
- 二重保存：`commit` は status の条件付き遷移で行い、二重に保存しない（`SESSION_STATE_CONFLICT`）

## 4.9 計測（D15）

- フェーズ1は分析用の SDK を使わず、`prompt_sessions` から集計する（10章）
  - テンプレートのバージョンごとの解析成功率（`parse_result`）
  - 離脱率（`status = abandoned` の割合）
  - use_case ごとの利用回数
- プロンプトの全文と、貼り戻した回答の生データは保存しない（D13）。そのため、解析失敗の原因調査は、回帰テスト用のサンプル（11章）で再現して行う
- 廃止：モデル名、トークン使用量、推定コスト、コスト異常の検知
