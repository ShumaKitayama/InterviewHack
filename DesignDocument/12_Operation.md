# 12. リリース・運用設計（Release / Ops）

> 改訂：2026-10-22。方針転換メモ（`DirectionChange_20261022.md`）の決定事項 D1〜D16 と 2.10 共通契約（特に 2.10.6）を反映した。

## 12.1 方針

- 個人開発で運営費をほぼ0円に保ちつつ、個人情報（職歴・面接内容）の取り扱いに耐える運用を最初から持つ
- 環境は `dev` / `prod` の2つ。`stg` はフェーズ2（TestFlight 配布）で追加する（2.10.6）
- 監視は「認可の越境兆候」「API のエラー率」「無料枠の使用量」「共有リンクの乱用」を最優先にする
- 障害時の基本戦略：止めるべきは「書き込み系（AI連携の commit、共有リンクの発行）」。閲覧系は可能な限り継続する
  - iOS アプリは読み取りキャッシュを持つため（D16）、サーバー停止中もユーザーは閲覧・復習を続けられる
- 課金・LLM API・Stripe は存在しない（D7・D8）。それに伴う運用（決済監視、クレジット整合、AI コスト監視）は行わない

---

## 12.2 環境構成（dev / prod）

| 要素 | dev | prod |
|------|-----|------|
| API | ローカルの Go（`go run ./backend/cmd/api`） | Cloud Run |
| DB | Neon の dev ブランチ | Neon の main ブランチ |
| 認証 | Firebase の dev プロジェクト | Firebase の prod プロジェクト |
| iOS | Xcode から実機・シミュレータ（dev の API に接続） | Xcode から開発者の実機（prod の API に接続） |

### 12.2.1 Neon（PostgreSQL）

- 1つの Neon プロジェクト内で、ブランチを環境ごとに分ける（`main` = prod、`dev` = dev）
- マイグレーションの事前確認用に、必要に応じて一時ブランチを作る（12.4）
- 無料枠ではアイドル時にコンピュートが停止し、初回アクセスで自動復帰する（コールドスタートあり）
- Cloud Run と Neon のリージョンは近接させる
- 無料枠の上限（ストレージ、コンピュート時間、ブランチ数など）は公式で要確認

### 12.2.2 Firebase Auth

- Firebase プロジェクトを環境ごとに分ける（dev / prod）
- 有効にするログイン手段：メールアドレス＋パスワード（Google は追加候補。D5）
- iOS アプリはビルド構成（`Debug-Dev` / `Release-Prod`）で `GoogleService-Info.plist` を切り替える（5.12）
- BFF は `FIREBASE_PROJECT_ID` で検証対象のプロジェクトを決める（`aud` の検証）

### 12.2.3 Cloud Run

- prod のみ。サービスを1つ置く
- 最小インスタンス数は 0（使われない間は停止し、費用を発生させない）
- 環境変数は 2.10.6 に従う（14.8 参照）

### 12.2.4 stg（フェーズ2で追加）

- TestFlight で他人に配布する段階で、Cloud Run の stg サービス、Neon の stg ブランチ、Firebase の stg プロジェクトを追加する
- それまでは、prod 反映前の確認を dev 環境と Neon の一時ブランチで行う

## 12.3 デプロイ設計（CI/CD）

詳細は 14 章を正とする。ここでは運用上の要点だけを記す。

### 12.3.1 リポジトリ/ブランチ戦略（最小）

- main: 本番
- feature/\*: 機能開発
- PR 必須、CI 通過必須（main への直接 push は禁止）

### 12.3.2 CI で必須のチェック

- Go：`go vet`、lint、`go test`、PostgreSQL サービスコンテナでの統合テスト、`scripts/arch_check.sh`
  - 統合テストには、少なくとも「認可の越境防止」「AI連携の commit の冪等性」「共有リンクの期限・失効」を含める
- iOS：`xcodebuild test`（`ios/` に変更があるときだけ）
- マイグレーションの冪等性検査（同じ SQL を2回適用しても失敗しないこと）

### 12.3.3 CD（デプロイ順序）

1. DB マイグレーション（prod、後方互換のもの）
2. バックエンドのデプロイ（Cloud Run）
3. スモークテスト（prod）

- prod へのデプロイは手動承認を必須とする（14.6）

---

## 12.4 マイグレーション運用（Neon）

- 変更はすべて `backend/migrations` の番号付き SQL で管理する（手作業で本番に当てない）
- 各 SQL は冪等に書く（`CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS`、`ADD COLUMN IF NOT EXISTS` など）
- 適用は `psql` で番号順に行う（2.10.2）
- prod へ当てる前に、Neon の main ブランチから一時ブランチを作り、そこで適用を確認する（本番データと同じ形で試せる）
  - 確認後、一時ブランチは削除する
- 破壊的変更（DROP、型変更）は原則禁止
  - 代替：新カラム追加 → 移行 → 旧カラム廃止（残す）
- enum は text + CHECK 制約で表現する（将来の変更に強い）

## 12.5 リリース手順（チェックリスト）

### 12.5.1 リリース前（dev と Neon の一時ブランチで必須）

- 認証（メールアドレス＋パスワード）でログインできる
- 認可の越境テスト（ユーザー U1 が U2 のデータを読めない・書けない）
- 主要フローが完走する
  - 想定Q&A：プロンプト作成 → 外部AIで実行 → 貼り戻し → プレビュー → 保存 → 復習
  - 面接ログ：入力 → 添削プロンプト → 貼り戻し → 保存
  - ES：企業研究資料の取り込み（URL / PDF / 画像）→ 要約 → ドラフト → 推敲 → 保存
- AI連携の commit を二重に送っても、二重保存されない
- 未完了の AI連携を、アプリ再起動後に再開できる
- 共有リンク：発行 → ログインなしで閲覧 → 失効後は 410 になる。期限切れも 410 になる
- オフラインで Q&A を閲覧・復習できる

### 12.5.2 本番反映（prod）

- Cloud Run の環境変数（`DATABASE_URL`、`FIREBASE_PROJECT_ID`、`SHARE_BASE_URL`、`APP_ENV`、`LOG_LEVEL`）が prod の値になっている。フィーチャーフラグ（12.11）が意図した値になっている
- `DATABASE_URL` が Neon の main ブランチを指している
- iOS アプリの `Release-Prod` 構成が prod の API と Firebase の prod プロジェクトを指している

## 12.6 監視・ログ設計（Observability）

### 12.6.1 監視対象（最優先）

- API の健全性（Cloud Run のログとメトリクス）
  - 5xx の発生率
  - レイテンシ（Neon のコールドスタートの影響を含む）
- AI連携
  - テンプレートのバージョンごとの解析成功率・離脱率（DB から集計。D15、10 章）
  - `SESSION_STATE_CONFLICT` の急増（クライアントの二重送信の兆候）
- セキュリティ
  - 401 の急増（攻撃の兆候）
  - 認証付き API の 404 の急増（他人の ID を指定する越境の試行の兆候。他人のリソースは 403 ではなく 404 を返すため）
  - 429 の急増（レート制限）
  - `/s/{token}` の 404 の急増（トークンの総当たりの兆候）
- 無料枠の使用量（超えると費用が発生する、または停止するため）
  - Cloud Run：リクエスト数、CPU・メモリ時間
  - Neon：ストレージ、コンピュート時間
  - Firebase Auth：認証の利用量
  - 各上限値は公式で要確認。定期的（月1回）に各コンソールで確認する

### 12.6.2 ログの種類

- アプリログ（iOS）
  - フェーズ1は Xcode のデバッグで確認する（分析用 SDK は入れない。D15）
  - 本文データはログに出さない
- BFF ログ（サーバー）
  - Cloud Run の構造化ログ（7.8.1）
  - `request_id`（相関 ID）と `release`（Git SHA）を必ず付与する
  - user_id は出してよいが、本文・メールアドレス・共有トークンは出さない
- DB の記録
  - `prompt_sessions`（status、parse_result、template_version）

### 12.6.3 アラート条件（例）

- 5xx 率 > 5%（10分平均）
- 401 / 404（認証付き API）/ 429 の急増
- `/s/{token}` の 404 の急増
- 無料枠の使用量が上限の 80% に到達
- フェーズ1は利用者が開発者本人のみのため、通知は Cloud Monitoring のメール通知（無料の範囲）で十分とする

## 12.7 障害対応（Incident Response）

### 12.7.1 重大度定義（例）

- SEV1：他人のデータが見える（認可の越境）、共有リンクで意図しない内容が公開される、データの消失・破損
- SEV2：API が広範囲に使えない（ログインできない、保存できない）
- SEV3：一部機能の不具合（特定テンプレートの解析失敗、表示崩れなど）

### 12.7.2 初動（SEV1/2 共通）

1. 影響範囲の特定（いつから、どのエンドポイント、何件）
2. 収束策の適用
   - 共有リンクの閲覧を一時停止する（フィーチャーフラグで `/s/{token}` を止める）
   - 書き込み系を一時停止する（AI連携の commit、共有リンクの発行）
   - 直前の Cloud Run リビジョンへロールバックする（12.8）
3. ログ・DB で原因を切り分ける
4. 復旧後に対応する（必要なら該当する共有リンクを一括失効する）

### 12.7.3 事後（Postmortem）

- 原因、再発防止、検知の改善（アラート閾値の見直し）
- テストケースの追加（11 章へフィードバック）

## 12.8 ロールバック戦略

- バックエンドは Cloud Run のリビジョン機能で、直前の安定リビジョンへ即時に切り戻す
- DB は原則ロールバックしない前提で、後方互換なマイグレーションを徹底する
- 破壊的変更が必要な場合は段階移行（新カラム追加 → 移行 → 切替）
- データ破損時は Neon の復元機能（ポイントインタイム復元、ブランチからの復元）を使う
  - 無料枠で遡れる期間は公式で要確認
- iOS アプリは、直前のコミットを Xcode で再ビルドして実機に入れ直す

---

## 12.9 バックアップ・リストア

- Neon の履歴保持（ポイントインタイム復元）を使う。無料枠での保持期間は公式で要確認
- 大きな変更の前（マイグレーション前など）は、Neon のブランチを作って復元点にする
- 最低限の復旧目標
  - RPO（許容データ損失）：24h 以内（MVP）
  - RTO（復旧時間）：数時間以内（MVP）
- フェーズ1は利用者が開発者本人のみのため、必要に応じて `pg_dump` で手元にもバックアップを取る

### 12.9.1 データの定期削除

- 期限切れ・失効した共有リンク（`share_links`）は、運用で定期的に物理削除してよい（月1回の無料枠の確認に合わせて手動の SQL で行う。保持期間は定めない。8.6）
- 退会したユーザーの `users` 行は、`deleted_at` を設定し email と display_name を消した状態で残す。定期的な物理削除は行わない（6.3.3）

---

## 12.10 サポート・問い合わせ運用

- フェーズ1は利用者が開発者本人のみのため、問い合わせ導線は設けない
- フェーズ2（TestFlight 配布）で追加する
  - 設定画面に「問い合わせ」リンク
  - 不具合報告テンプレート（発生日時、画面、操作、request_id）
  - 対応フロー：request_id で Cloud Run のログを確認 → 該当ユーザーの `prompt_sessions` などを確認 → 修正
- 課金がないため、課金に関する問い合わせ対応は存在しない（D14）

---

## 12.11 フィーチャーフラグ（運用の安全弁）

- 以下を ON / OFF できるようにする。フラグは Cloud Run の環境変数で管理する（MVP）

| 環境変数 | 内容 | 既定値 | 停止時の応答 |
|----------|------|--------|-------------|
| `FEATURE_SHARE_VIEW` | 共有ページ（`/s/{token}`）の閲覧 | `on` | 503 の「一時停止中」HTML |
| `FEATURE_SHARE_CREATE` | 共有リンクの発行 | `on` | 503 `FEATURE_DISABLED` |
| `FEATURE_COMMIT_DISABLED_USE_CASES` | commit を止めるユースケース（カンマ区切り。例：`qa_generate,es_refine`） | 空（すべて有効） | 503 `FEATURE_DISABLED`（セッションは `pasted` のまま） |

- 値を変えると Cloud Run の新しいリビジョンが作られ、反映される

## 12.12 この章の凍結事項

- 環境は dev / prod の2つ。stg はフェーズ2で追加する
- 監視は「認可の越境」「API のエラー率」「無料枠の使用量」「共有リンクの乱用」を最優先にする
- マイグレーションは冪等な SQL を `psql` で番号順に適用し、prod 前に Neon の一時ブランチで確認する
- DB は後方互換マイグレーションを原則とし、ロールバックに頼らない
- 無料枠の数値は設計書に断定して書かず、公式で確認する
